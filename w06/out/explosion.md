# Task 2: Explosion curve

측정 환경은 Windows 11, Python 3.13.9, Intel CPU이다. 측정값은 `explosion.json`의
`tracemalloc` 결과를 사용했다.

| support | frequent pairs | peak counters | time (s) | peak memory (MB) |
|---:|---:|---:|---:|---:|
| 400 | 249 | 10,585 | 0.76 | 1.1 |
| 200 | 776 | 58,626 | 1.26 | 6.4 |
| 100 | 2,244 | 273,701 | 2.63 | 26.4 |
| 50 | 6,397 | 820,259 | 4.59 | 102.2 |
| 25 | 17,045 | 893,456 | 6.09 | 102.2 |
| 12 | 43,116 | 893,456 | 4.67 | 102.8 |
| 6 | 101,938 | 893,456 | 4.99 | 119.4 |
| 3 | 250,054 | 893,456 | 4.61 | 156.7 |

support 3까지 측정했지만 프로세스가 중단될 정도의 메모리 부족은 발생하지 않았다.
따라서 이 데이터와 컴퓨터에서는 support 3도 실행 가능한 범위였고, 실제 오류가
발생한 지점은 관찰하지 못했다. 현재 기록된 가장 낮은 support는 3이다.

support를 절반으로 낮출 때 peak counter는 10,585 → 58,626 → 273,701 →
820,259로 크게 증가했다. 대략 5.5배, 4.7배, 3.0배 증가로, 선형 증가보다
빠르지만 마지막에는 생존 가능한 item 조합 수의 한계 때문에 증가가 둔화된다.

반면 실제 frequent pair 수는 249 → 776 → 2,244 → 6,397 → 17,045로
증가했다. 답의 개수보다 계산 중 유지해야 하는 후보 counter 수가 훨씬 빠르게
증가한다. 즉, threshold를 조금 낮추는 것만으로도 결과는 조금 늘어나는 반면
메모리 비용은 급격히 커지는 것이 이 실험의 핵심이다.
